The Rent You Pay Every Turn

I audited three months of my own Claude sessions — every API call, every token. The bill wasn't where I thought it was, and fixing it isn't about typing less. It's about the shape of the session.

Elvin Peters · August 2026 · Data: 95 sessions, 43,373 API calls, parsed from raw transcripts

$16.7KAPI-equivalent cost

The model never remembers. You re-send everything.

The single most important fact about working with an LLM assistant: the API is stateless. There is no server-side memory of your conversation. Every single call — every tool result, every reply — re-transmits the entire accumulated context: the chat history, every file it ever read, every screenshot, every command output. Caching makes the re-send 10× cheaper per token, but it cannot make it free, and the volume is staggering.

Think of context as rent. Every file you pull into a session isn't a one-time cost — it's a tenant. It occupies the window and gets re-paid on every subsequent call until the session ends or the context is purged. A 50,000-token file read early in a 1,000-call session costs roughly 50 million tokens over its lifetime.

Output was 13% of my bill. The other 86% was re-reading things I'd already read.

The sawtooth: what a marathon session actually looks like

My biggest session ran 6,940 API calls and 3.56 billion tokens — book editing, builds, scrapes and fixes all in one endless window. Below is its actual per-call context, parsed from the transcript. It climbs to the 1M-token ceiling, auto-compacts (the tool summarizes old history to make room), and climbs straight back. Eight times.

Each tooth is the same story: rent compounding until the landlord forces a reset. The average call in that session carried ~500K tokens of context — most of it stale tool output and files whose moment had passed.

Here's the counterintuitive part: on a cumulative chart this session looks like a clean straight line — which reads as "nothing's wrong." But linear growth just means per-call cost saturated at the maximum. An efficient session's line is also straight — just five to ten times shallower. The slope is the diagnosis.

Three session shapes

The fix is not a rule like "use fewer tokens." It's recognizing that different work wants differently-shaped sessions — and that the expensive failure is mixing shapes. One of these three patterns fits almost every task:

Anti-pattern

The Marathon

  • One window, every task: edits, builds, scrapes, questions
  • Context rides at 500–990K; compaction fires at the ceiling
  • Small tasks pay the big task's rent
My Jul 16 session: 3.56B tokens. Same work as ~5 separate sessions at a fraction of the cost.
Default

The Assembly Line

  • One task = one session. Ship, checkpoint, start fresh
  • Subagents do the reading; only conclusions enter the window
  • Read sections (grep first), not whole files
  • Purge at task boundaries, not at the ceiling
My median session: 36M tokens — about 1% of a marathon. This shape already works; it just wasn't the habit.
Declared, deliberate

The Studio

  • For judgment work that genuinely needs the whole corpus — a manuscript's voice, a system's architecture
  • Load exactly that corpus up front, then stop adding
  • Batch questions — every turn re-pays the full window
  • Hard stop near the ceiling: checkpoint, end, don't extend
Big context on purpose is fine. Big context by accident is a leak. Declare which one you're in.

Where the tokens actually enter: the Read multiplier

Across 20,487 tool calls, one tool injected 87% of all content that entered my contexts: plain file reads. 2,733 Reads pushed ~37M tokens of file text into sessions — and each one then sat in the window collecting rent for hundreds of calls. Meanwhile the one tool designed to prevent this — delegating reads to a subagent, whose context is disposable — was used 451 times in three months. The least-used lever was the highest-value one.

Habits that fix it (the harness only nags — these decide)

I now run automated guardrails — a hook that warns at context bands, and a forced purge at 250K instead of the 1M ceiling. But automation only clamps the damage. The gains come from habits at three moments: before a session, before a read, and after a milestone.

  1. Open with a shape.Ten seconds before starting: is this an assembly-line task or studio work? If the current session's context doesn't serve the new task — new session. Never "while I have you here…" a heavy window.
  2. The three-question gate before any file enters context.① Do I need the whole file, or a section? ② Could a subagent fetch just the conclusion? ③ Will future turns in this session need this content again? Two noes = it doesn't belong in the main window.
  3. Delegate reads by default.Any investigation spanning more than 2–3 files goes to a subagent or explore agent. Its context is disposable; only the answer comes back. This directly attacks the 87% line.
  4. Purge at boundaries, not ceilings.Milestone shipped → checkpoint the state file → compact or clear → next task. A purge you choose keeps what matters; a purge at the window edge keeps what fits.
  5. Batch questions to heavy sessions.In a studio session every message re-pays the full window. Five drive-by questions asked separately cost 5× one combined turn. Collect, then ask once.
  6. Outputs live on disk, not in chat.Agent results, reports, drafts → files. The session reads back the synthesis, not the transcript. Saved state is what makes the next fresh session cheap.
  7. Tier the model to the task.Mechanical work (renames, formatting, categorizing, bulk edits) runs on the cheap tier — including inside subagents. The top tier is for judgment. See the chart below for what this is worth.
  8. Weekly hygiene.Prune memory files and CLAUDE.md; audit standing MCP tools. Everything auto-loaded is rent paid on call one of every session, forever.

Model choice: the newest model in each tier wins

Three months of blended cost — what my tokens actually cost per million across cache reads, writes and output — makes the model story simple. Within a tier, the newer generation is strictly better: same or lower effective price, and smarter, which quietly compounds — a sharper model finishes in fewer calls, wanders less, and re-reads less, so the efficiency gain is bigger than any price sticker shows.

The one nuance: the top tier (Fable 5) isn't "worse" — it's a scalpel. At 2.4× the blended cost of Opus, it earns its price on the hardest judgment work and loses it on marathons of routine tasks. The ladder: newest Sonnet for mechanical, newest Opus as the daily driver, the frontier tier reserved for the work that actually needs it.
