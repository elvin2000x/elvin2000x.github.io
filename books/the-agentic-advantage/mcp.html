MCP Servers & Integrations

Kept current · updated July 2026

Also online, free. This appendix is on the web in copy-and-paste form, kept current, at elvinpeters.com/books/the-agentic-advantage/mcp.

When I need an agent to work inside a platform that someone else already maintains, I reach for the Model Context Protocol before I write a single line of custom tool code. MCP is an open standard that lets any compatible agent host plug into a pre-built "server" for a service such as GitHub, Slack, or a database, so the agent inherits a whole set of ready-made tools without me building or maintaining the integration myself. A large share of everyday operator needs, reading and writing files, pulling issues, posting messages, querying records, is already covered by a published server. This appendix is a working reference for the servers worth knowing, how to wire one in, and the security posture you need before you trust one.

What MCP Gives You

Before MCP, every agent framework invented its own way of describing tools, so connecting a model to a data source was a custom job each time. MCP standardizes that connection the way USB-C standardized a charging port. A tool provider writes one server, and any MCP-compatible client can consume it. At the time of writing, the compatible clients include Claude Desktop, Claude Code, Cursor, Windsurf, VS Code, and the agent SDKs from the other major model providers, which is why a server you adopt is portable across hosts instead of locked to one.

The practical rule for when to use it: reach for an MCP server when a maintained one already exists for the system you need, when the same capability should be reusable across more than one agent or person, or when you want a clean audit boundary between the agent and the capability. Write a plain in-process function instead when the tool is app-specific, latency-sensitive, or so trivial that a server's overhead outweighs the payoff.

Most former first-party integrations were handed to their respective vendors, so for platform servers you generally install the vendor-maintained or official build. A note on provenance, because it trips people up: many of these platform servers began as first-party demos and were later moved to vendor-maintained or archived repositories, with maintenance handed to the platform owner. The GitHub server in particular was rewritten and now ships as an official vendor build rather than the original demo. When you install one, take the current vendor-maintained or official version rather than an archived early build. The Agentic Advantage Toolkit is kept current with the live registry links, so use it as the up-to-date pointer whenever a server has moved, since the ecosystem changes faster than any printed page can.

There is also an official MCP Registry that acts as the canonical index of published servers, with an open specification so third-party catalogs can federate off it. At the time of writing it holds on the order of two thousand entries and is the right first stop when you are hunting for a server for a specific platform.

How to Add One

Adding a server comes down to two things: a config entry that tells your agent host how to launch or reach the server, and credentials supplied in a way the model never sees.

Local servers run as a subprocess on your own machine and talk to the client over standard input and output, so they need no network stack. You register one with a small entry naming the command to run, its arguments, and an optional environment block for secrets. The shape is the same across hosts:

json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/allowed/dir"],
      "env": {
        "SOME_API_KEY": "value-loaded-from-your-environment"
      }
    }
  }
}

The command-line equivalent adds the same server without hand-editing the file. In Claude Code, for example, you run an "add" command that takes the server name, the launch command, and any environment variables, and it writes the entry for you.

Remote servers are added by URL instead of a launch command. On first connection the server negotiates an OAuth flow, so you authorize it once in a browser and the host stores the resulting token. There is no key to paste into the config at all:

json
{
  "mcpServers": {
    "example-remote": {
      "url": "https://mcp.example.com/endpoint"
    }
  }
}

Credentials, the important part. For local servers, secrets go in the env block, which is passed to the server process and stays out of the model's context entirely. For remote servers, the OAuth flow keeps the token in the host, and the model never handles it. The rule that follows from this: secrets live in the server's environment or in an OAuth token, never in a tool description, a tool argument, or a resource body that the model can read. If a server ever asks you to pass a key as a visible argument, treat that as a red flag rather than a convenience.

Once a server is registered, the host launches it, lists its tools at startup, and injects the tool schemas into the agent's context so the model can call them. From that point the agent uses the server's tools the same way it uses any built-in tool.

Security: Treat Tool Definitions as Untrusted Input

MCP hands a model live access to real tools, which is exactly what makes it powerful and exactly what makes it a threat surface. Security research across thousands of deployed servers has found that a significant share carry at least one exploitable weakness, so the convenience of a pre-built server is never a reason to skip the vetting.

The sharpest edge is that a tool's description is text the model reads and trusts, yet the user rarely sees it. In a tool-poisoning attack, a server hides malicious instructions inside the description or schema, for example telling the model to also read a private key file and pass its contents as an innocent-looking argument. The model obeys because it treats tool metadata as authoritative. A related move is the "rug pull," where a server is benign at approval time and then silently mutates its tool definitions after you have granted trust. A third variant is indirect injection through returned data, where a fetched web page or an issue body carries instructions and the model treats retrieved content as commands rather than as data.

The defenses are practical and worth applying to every server you adopt:

  • Pin and diff the definitions. Pin server versions and verify them by hash instead of pulling the latest build at runtime. Show the full, unabbreviated tool description to a human at approval time, and re-prompt whenever a definition changes. Comparing the current definition against the approved one is what defeats a rug pull.
  • Scope narrowly and run least-privilege. Give a filesystem server the narrowest possible root rather than the whole drive, hand a database server a read-only role when it never needs to write, and request scoped tokens rather than wildcard grants. A server rooted too broadly becomes a lever for escalation.
  • Treat all tool output as data rather than instructions. Retrieved content is external input, so hold it to the same suspicion you would apply to any untrusted source, and never let a returned page redirect the agent's task.
  • Self-host or vet the source. For anything sensitive, prefer a server you host and control, or one whose code you have reviewed, over an anonymous package pulled fresh at launch. Runtime-fetched packages carry supply-chain risk, since a single compromised release runs on your machine with your environment.

Newer versions of the protocol tighten authorization and add a formal lifecycle for deprecating features, which closes some of these gaps at the standard level. Description-level poisoning, though, stays fundamentally a trust-boundary problem that you handle in how you approve and monitor servers rather than something the protocol can fully solve for you. Adopt servers the way a cautious operator adopts any third-party dependency: pin it, scope it, read what it actually does, and re-check it when it changes.

Server names, registry contents, and version details in this appendix are current as of the time of writing. MCP is one of the faster-moving corners of the agent ecosystem, so treat the live registry and the accompanying Toolkit as the authoritative, continuously updated source.
